10	
11	| Column | Type | Meaning |
12	|---|---|---|
13	| `timestamp` | datetime64, tz-naive | Session date |
14	| `open`, `high`, `low`, `close` | float64 | Adjusted prices |
15	| `volume` | float64 | Shares traded |
16	| `symbol` | str | Ticker |
17	
18	Coverage is not uniform. SPY, QQQ and the sector SPDRs trade across the whole
19	window; HYG starts in April 2007.
20	
21	The 25 symbols were chosen in 2026, from ETFs that are liquid today. Which
22	tickers are on the list at all therefore reflects hindsight.
23	
24	## `eligibility.csv`
25	
26	Point-in-time membership, one row per (symbol, year) the symbol was eligible
27	for: `symbol, eligible_year`.
28	
29	A symbol is eligible for calendar year Y when, over year Y-1, its average daily
30	dollar volume was at least $10M across at least 200 sessions. The threshold is
31	not inflation-adjusted. A symbol absent from a year has no row for that year.

@feature(
    name="rsi",
    category="momentum",
    description="Relative Strength Index - momentum oscillator measuring speed and change of price movements",
    normalized=True,
    value_range=(0.0, 100.0),
    formula="RSI = 100 - (100 / (1 + RS)) where RS = Average Gain / Average Loss",
    ta_lib_compatible=True,
    input_type="close",
    references=["Wilder, J. W. (1978). New Concepts in Technical Trading Systems"],
    tags=["oscillator", "momentum", "overbought", "oversold"],
)
def rsi(
    close: npt.NDArray[np.float64] | pl.Series | str,
    period: int = 14,
) -> npt.NDArray[np.float64] | pl.Expr:
    """
    Relative Strength Index with Wilder's smoothing.

    RSI is a momentum oscillator that measures the speed and change of price
    movements. Values above 70 typically indicate overbought conditions,
    while close below 30 indicate oversold conditions.

    Parameters
    ----------
    close : array-like or column name
        Price data (typically closing close)
    period : int, default 14
        Number of periods for RSI calculation
    implementation : str, default 'auto'
        Implementation to use: 'auto', 'numba', or 'polars'

    Returns
    -------
    array or Polars expression
        RSI close on 0-100 scale

    Examples
    --------
    >>> import numpy as np
    >>> close = np.array([44, 44.34, 44.09, 44.15, 43.61, 44.33, 44.83, 45.85, 47.15, 47.72])
    >>> rsi_14 = rsi(close, period=5)  # Using 5 for demo
    >>> rsi_14[5:]  # First 5 close are NaN
    array([57.97, 62.93, 70.46, 74.53, 70.61])

    Notes
    -----
    - Uses Wilder's smoothing (not simple EMA) for exact TA-Lib compatibility
    - RSI = 100 - (100 / (1 + RS)) where RS = Average Gain / Average Loss

    def _should_use_calendar_splitting(self) -> bool:
        """Determine if calendar-first splitting should be used.

        Calendar splitting is used when:
        1. A calendar is configured (always true now with NYSE default), AND
        2. Time-based sizes are used (str test_size/train_size), OR
        3. The config has filter_non_trading=True (default)
        """
        if self.calendar is None:
            return False

        # Time-based sizes always need calendar
        if isinstance(self.test_size, str) or isinstance(self.train_size, str):

        # Calendar filtering of non-trading rows
        if self.config.filter_non_trading:
            return True

        return False

## Step 4 done — why not a random split

Trained 5 expanding-window LightGBM folds (`WalkForwardCV(n_splits=5, label_horizon=21, timestamp_col="timestamp")`). Each fold's train window ends roughly a month before validation starts — that's the `label_horizon=21` purge automatically removing the training rows whose forward-return window would otherwise overlap the validation period.

A random train/test split would be wrong here for two compounding reasons:
1. **The label itself overlaps across time.** `fwd_ret_21` at date *t* and at date *t+1* share 20 of their 21 forward daily returns. A random split would scatter these overlapping-label rows across train and validation, so a training row could directly leak the realized returns that make up a validation row's label — not just correlation, near-duplication.
2. **Live deployment never has future data to train on.** A random split lets the model train on rows dated after the ones it's tested on, which can't happen when the model is actually used going forward. `WalkForwardCV` keeps train always-before-validation and purges the overlap window, so the CV score reflects what the model could actually know at prediction time.

- **`entity_col="symbol"` is mandatory.** I'm passing the same `oof` frame as both `predictions` and `returns`. Why I expect naive and HAC t-stats to differ: the naive t-stat treats each day's IC as an independent observation. Because the label horizon is 21 sessions, consecutive days' ICs are built from almost the same forward-return data and are strongly positively autocorrelated — that inflates the *effective* variance of the mean IC estimate without inflating the naive standard error (which assumes independence). HAC/Newey-West with `label_horizon=21` lags absorbs that autocorrelation into the standard error, so I expect `hac_se > naive_se` and correspondingly `|t_stat| < |naive_t_stat|`.
